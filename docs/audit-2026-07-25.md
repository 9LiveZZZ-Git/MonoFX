# MonoFX suite — code audit, 2026-07-25

> **Status: all findings remediated.** Every C/H/M/L item below is fixed; the suite has grown from
> 60 to **80 assertions** and is green. Section 0.5 records what changed, which numbers moved as a
> result, and — importantly — the two places where the *audit itself* was wrong and the fix work
> corrected it. The finding text below is left as originally written so the reasoning stays
> auditable; read it as history, not as the current state of the code.

Scope: every file in the repository at commit `98fd48a`. Baseline `npm test` was **60/60 green**
before and after the audit pass; nothing was modified while auditing.

Every claim below was produced by executing code against the shipped sources. Repro scripts live
outside the repo (session scratchpad); the measured output is quoted inline so the numbers can be
checked without them.

---

## 0. Verdict in one paragraph

**The central claim holds.** The mono sum of all four MonoFX cores is genuinely independent of the
width control — verified across the full parameter-extreme cross product at six sample rates from
22.05 kHz to 192 kHz, worst deviation `2.2e-16` (one to two ULP of float64 output rounding, not
width leakage). The reverb's Householder matrix is exactly orthogonal, the COLA constants are
right, `mix=0` is bit-transparent, and the engine is deterministic. The DSP thesis is sound and the
implementation of that thesis is correct.

**What is not sound is everything around the thesis.** `LiveCore` — the one piece of real code
shared between MonoLock live mode and the offline dual-resolution render, and the designated bridge
to the JUCE port — corrupts its output at most host buffer sizes and has a latency that varies with
the host quantum, while the docs state it as a fixed number. The offline renderer fades in the
first 37 ms of every file it produces. Both AudioWorklet wrappers destroy the mono signal on a mono
track. And the "VERIFY" button shipped to prove the product's core claim prints a reassuring
sentence regardless of what it measured. None of these are visible to `npm test`, which is why the
suite is green.

## 0.5 Remediation

### Where this audit was wrong

Two findings were misattributed. Both were caught by measuring during the fix rather than trusting
the diagnosis, and both are worth recording because the wrong explanation was the plausible one.

- **H8 blamed the missing per-band auto-amount. It is the forced bass-mono, and nothing else.**
  The finding reasoned that `LiveCore` lacks the offline engine's `autoS = 1-smoothstep(0.90,0.98,
  bandPre)` back-off and therefore over-processes already-compatible material. Disabling each
  suspect in turn shows the rotation path is not the cause: with bass-mono off, `LiveCore` leaves
  the suite's `wide` case at **0.291** against an input of 0.288 — *more* transparent than the
  offline engine's 0.323. Unconditional bass-mono was doing all of the collapsing. It is a
  deliberate mastering behaviour, so the fix is to make it switchable (`bassMono`, default 1), not
  to remove it. The real defect was that a deliberate behaviour had no off switch.

- **H7 was reported as a phaser defect. It is systemic across all four cores.** The phaser was
  simply the worst case (4.58 dB) and the only one measured. A test written during the fix
  (`width widens without panning the image`) found the delay at **5.24 dB**, the chorus at 1.67 dB
  and the reverb at 0.61 dB. The mechanism is general: `outL=m+s` / `outR=m-s` carry unequal energy
  whenever `E[m·s] != 0`, and every core builds its width term from material the mid path already
  contains.

### What the new tests found that the audit did not

Writing the regressions surfaced three defects the audit missed outright:

| Defect | Detail |
|---|---|
| Phaser unstable at maximum settings | Peak **15.32×** full scale on a sustained sweep at `fb=0.9`. The old test used `drums()`, which is nearly all transient, so the resonance never had time to build. Fixed by scaling the chain input by `(1-fb)`, pinning the resonant peak at unity; peak is now 1.62×. |
| Reverb runs away on a negative `damp` | `damp=-14000` makes `lpc` negative and the one-pole diverges to `-2.8e8`. |
| Delay runs away above `fb=1` | `fb=3.6` reaches 1354× full scale. |

All three are now covered by `out-of-range parameters stay finite and bounded`, which probes every
`PARAMS` entry past both ends of its declared range.

## 1. Findings by severity

Severity key — **critical**: breaks a stated invariant or emits corrupt audio · **high**: audibly
wrong output or a crash under normal host conditions · **medium**: wrong under reachable but
unusual conditions, or a false-green test · **low**: latent hazard, doc-vs-code mismatch, or
real-time-safety debt.

### CRITICAL

#### C1 · `LiveCore` destroys audio when the host block exceeds `fifoCap`
`src/monolock-engine.generated.js:633` (`fifoCap = W*4`), consumed at `:741-758`

`processBlock` pushes every completed frame's `hop` samples into a ring of `W*4` samples, then
reads `N` samples out. The write path saturates the count (`fCnt = Math.min(cap, fCnt+1)`) but never
advances `fRd`, so once a single call produces more than `cap` samples the writer laps the reader and
unread audio is overwritten.

At `W=512` the cap is 2048 samples. Rendering 1 s of pink noise through identical channels:

```
Q       out RMS    corr(L,R)
128     0.70920    0.9855
2048    0.70920    0.9855
4096    0.49831    0.9857   <-- Q > fifoCap: 50.4% of the render is digital silence
8192    0.35125    0.9860   <-- 76.0% of the render is digital silence
```

Reachable in offline bounce/freeze (hosts routinely hand a render thread 4096+), and at
`W=512` with any host configured above a 2048-sample buffer. Not reachable in the browser
prototype, where the AudioWorklet quantum is fixed at 128 — this bites the JUCE port.

**Fix:** size the FIFO from the host's `maximumExpectedSamplesPerBlock` (JUCE gives it in
`prepareToPlay`), or drain into the caller's output buffer directly instead of via a fixed ring.

#### C2 · `LiveCore` injects mid-stream dropouts at incommensurate block sizes
`src/monolock-engine.generated.js:752-758`

Independently of C1, the read loop emits a zero and does **not** advance `fRd` whenever `fCnt`
reaches 0. Because production is chunky (`hop` samples at a time) and consumption is chunky (`N` at
a time), the FIFO underruns in steady state whenever `N` is not commensurate with `hop = W/4`.
Those injected zeros are not a delay — they stretch the stream, so the output is permanently
damaged rather than merely late.

Ground truth by exhaustive best-shift comparison against a `Q=128` reference (`W=512`):

```
Q      bestShift  max|diff|   verdict
64     64         0.00e+0     IDENTICAL (pure delay)
100    124        0.00e+0     IDENTICAL (pure delay)
256    0          0.00e+0     IDENTICAL (pure delay)
333    105        2.18e+0     CORRUPTED
480    96         0.00e+0     IDENTICAL (pure delay)
1000   117        1.09e+0     CORRUPTED
1024   0          0.00e+0     IDENTICAL (pure delay)
```

Confirmed end-to-end on a full render, counting runs of exact zeros in the interior of the output:

```
Q       bestShift  max|diff|   interior zero-runs   verdict
128     0          0.00e+0     0                    clean (pure delay)
441     120        1.01e+0     9                    *** CORRUPTED ***    <- 10 ms at 44.1 kHz
480     96         0.00e+0     0                    clean (pure delay)
735     125        4.16e-1     1                    *** CORRUPTED ***    <- 16.7 ms at 44.1 kHz
882     119        9.27e-1     5                    *** CORRUPTED ***    <- 20 ms at 44.1 kHz
1024    0          0.00e+0     0                    clean (pure delay)
1470    124        0.00e+0     0                    clean (pure delay)
2048    0          0.00e+0     0                    clean (pure delay)
```

Confirmed corrupted: 333, 441, 735, 882, 1000, 2049. Whether a given incommensurate size actually
underruns depends on how the arithmetic lands — 1470 is incommensurate with `hop` but survives this
render, so the rule is "can inject dropouts", not "always does". That is worse than a clean rule,
not better: it means the failure is buffer-size- and content-dependent and will not reproduce on the
developer's machine. 441, 735 and 882 are the standard 10 / 16.7 / 20 ms buffers of a 44.1 kHz
session. VST3 permits any block size up to the declared maximum, and hosts split blocks at
automation boundaries, so this is not exotic.

**Fix:** the same restructure as C1. A correctly sized FIFO with a proper full/empty policy removes
both failure modes.

### HIGH

#### H1 · `LiveCore` latency is not constant, and the documented figures are test artifacts
`src/monolock-engine.generated.js:732-758`; claims in `README.md:66` and `CLAUDE.md`

The algorithmic latency is `W - hop`, but the FIFO primes with a variable number of leading zeros
depending on how the host quantum divides `hop`, so the observed latency moves. Measured by
cross-correlating the output against the input (peak correlation 1.0000 in every row):

```
W     Q      lag(smp)  ms      docs claim
512   32     480       10.00   8.0 ms   MISMATCH
512   64     448        9.33   8.0 ms   MISMATCH
512   128    384        8.00   8.0 ms   ok
512   480    480       10.00   8.0 ms   MISMATCH
512   1024   384        8.00   8.0 ms   ok
1024  32     992       20.67   18.7 ms  MISMATCH
1024  128    896       18.67   18.7 ms  ok
1024  256    768       16.00   18.7 ms  MISMATCH
1024  1024   768       16.00   18.7 ms  MISMATCH
```

The `18.7 ms` in the README is not the engine's latency — it is `16.0 ms` of algorithmic latency
plus `128` samples of FIFO priming, i.e. an artifact of the test happening to use `Q=128`. The true
algorithmic figure for `W=1024` is 16.0 ms.

This matters more than a wrong number in a doc: `setLatencySamples()` must be a constant that the
host can compensate. A latency that changes with the buffer size cannot be reported correctly, and
the error shows up as a time-smeared mix — the exact defect this product exists to fix.

**Fix:** make the priming deterministic (pre-fill the FIFO with `W-hop` zeros at reset), report
`W-hop`, and add a test that asserts the measured latency is identical across block sizes.

#### H2 · The offline renderer attenuates the first 37 ms of every file
`src/monolock-engine.generated.js:461-467`

The overlap-add loop starts at frame 0, so samples before the window fully overlaps receive fewer
than the `W/hop = 8` contributions the `/4` normalisation assumes. The COLA constant itself is
**correct** (verified by summing the actual windows: `3.999999821..4.000000137` at `hop=W/8`); the
problem is only the un-overlapped head.

On an already-mono-compatible file (identical channels), which must be passed through untouched:

```
region                  gain ratio   error
samples     0-  128     0.005931     -44.54 dB
samples   128-  256     0.019882     -34.03 dB
samples   512-  640     0.187512     -14.54 dB
samples  1024- 1152     0.676909      -3.39 dB
samples  1536- 1664     0.982115      -0.16 dB
samples  1792- 1920     1.000000       0.00 dB
8192..n-8192 (TESTED)   1.000000    -122.9 dBFS
```

Output sample 0 is `0.000000` against an input of `-0.172916`. Transparency is reached at sample
1787 (37.2 ms). The tail is fine — `outL` is `n+NFFT` long so the final frames complete normally.

The regression suite asserts only over `8192 .. n-8192` (`tests/monolock-engine.test.js:100`), which
is precisely why this has never shown up. The WAV export writes `proc.oL[i]` from `i=0`
(`prototypes/monolock-prototype.html:1447`) with no compensation, so every exported file carries the
fade. For a repair tool applied to finished masters, clipping the attack off the first transient is
a shipping defect.

**Fix:** either run `⌈(W-hop)/hop⌉` priming frames over zero-padded input before sample 0, or
divide by the actual accumulated window-square envelope instead of the constant 4. Then widen the
transparency assertion to cover the whole buffer.

#### H3 · Both AudioWorklet wrappers destroy the signal on a mono bus
`prototypes/monofx-suite.html:197` and `src/monolock-engine.generated.js:777`

Both wrappers do:

```js
this.core.processBlock(i[0], i[1]||i[0], o[0], o[1]||o[0], i[0].length);
```

On a mono output bus `o[1]` is undefined, so `outL` and `outR` are the **same** `Float32Array`.
Every core ends with `outL[i]=m+s; outR[i]=m-s;` — the second write overwrites the first, and the
host receives `m - s` instead of `m`.

The side term is not zero on a mono input, because in every core `S` is synthesised from the mid
path (phaser stage-3 minus stage-6, chorus voice-1 minus voice-3, delay's opposite-sign ring, reverb's
alternating-sign tap). Measured against the intended mono output over 3 s:

```
core     RMS(intended m)  RMS(actual m-s)  error vs signal
PHASER   0.08816          0.10404          -8.2 dB
DELAY    0.11641          0.11524          -15.7 dB
REVERB   0.08005          0.07921          -12.5 dB
CHORUS   0.09680          0.09602          -8.7 dB
```

The irony is exact: on a mono track the suite subtracts the decorrelated side content from the mono
signal — the interference artifact the entire product is designed to make impossible.

**Fix:** write `m` directly when the output is mono, or refuse to alias:
`const R = o[1] || o[0]; if (R === o[0]) { /* mono path: emit m */ }`.

#### H4 · The shipped VERIFY button states its conclusion regardless of the measurement
`prototypes/monofx-suite.html:358-374`

The status string is assembled with the interpretation hardcoded:

```js
'· mono-sum deviation width 0→1: ' + db.toFixed(1) +
' dBFS (1 ULP float32 floor) · stereo corr @ width=1: ' + corr.toFixed(3) +
' · mono listeners hear the identical effect at any width'
```

There is no threshold, no pass/fail, and no colour change. Feeding it a `PhaserCore` deliberately
broken so that 1 % of the width-dependent side term leaks into the mid path — precisely the
invariant the product rests on:

```
healthy: mono-sum deviation width 0→1: -138.5 dBFS (1 ULP float32 floor) · ... identical effect at any width
BROKEN : mono-sum deviation width 0→1:  -41.2 dBFS (1 ULP float32 floor) · ... identical effect at any width
```

`-41.2 dBFS` is a catastrophic failure being described to the user as the float32 rounding floor.
The `npm test` assertion on the same broken core correctly fails (`f64 -41.2 dB`, threshold `1e-15`).

**Fix:** measure in float64 like the test does, compare against a threshold, and print PASS/FAIL.
A verification tool that cannot fail is not a verification tool.

#### H5 · A single NaN or Inf poisons the phaser permanently
`src/monofx-phaser.js:42`

`this.fbS = Math.abs(x)<1e-24 ? 0 : x` is a denormal flush, and `Math.abs(NaN) < 1e-24` is `false`,
so NaN passes straight through. The six allpass states `x1[]`/`y1[]` have no guard at all. One bad
input sample latches all thirteen state variables:

```
core     input      recovery
PHASER   NaN        *** PERMANENTLY POISONED (still NaN after 2.1 s of clean audio) ***
PHASER   Infinity   *** PERMANENTLY POISONED ***
DELAY    NaN        recovers after 0 blocks
REVERB   NaN        recovers after 0 blocks
CHORUS   NaN        recovers after 1 block (11 ms)

after one NaN sample:  fbS=NaN  x1=[NaN x6]  y1=[NaN x6]
```

An upstream plugin glitch silences the channel until the user re-instantiates.

**Fix:** guard with `Number.isFinite(x) ? (Math.abs(x)<1e-24 ? 0 : x) : 0` and apply it to the
allpass states too. In C++, `ScopedNoDenormals` handles the denormal half but not the NaN half.

#### H6 · Reverb `refresh()` wipes the tail on any SIZE or DECAY move
`src/monofx-reverb.js:35`

`refresh()` runs at the top of every `processBlock`, and any change that moves a rounded line length
executes `this.bufs[i].fill(0); this.ptrs[i]=0;`, destroying the entire recirculating state.

```
tail RMS before a 1.00 -> 1.05 size move: 4.419e-2
tail RMS in the very next block         : 0.000e+0    (identically zero, not merely quiet)
```

A knob drag from 1.0 to 2.0 produces 35 395 samples of exact digital silence. Reverb size is a
routinely automated parameter.

**Fix:** keep the buffers, move only the read/write pointers, and crossfade between old and new
line lengths — or at minimum interpolate the length rather than reallocating.

#### H7 · Phaser width control pans the image rather than widening it
`src/monofx-phaser.js:45`

`sOut = S + wS*(y3-x)` injects the stage-6 output `x` into the side with weight `-wS`, while the mid
path `wet = 0.5*(M+x)` (line 43) already carries the same `x` with weight `+0.5*mix`. The two output
terms are strongly anti-correlated, so `m+s` and `m-s` do not carry equal energy — WIDTH acts as a
frequency-dependent panner. On a mono source at factory defaults:

```
width=0.0  imbalance  0.000 dB   corr(L,R)=1.000
width=0.5  imbalance -0.950 dB   corr(L,R)=0.895
width=1.0  imbalance -1.643 dB   corr(L,R)=0.633
```

At `width=1, mix=1` the imbalance is `-4.93 dB`; at all-max, `-5.49 dB`. The bias is one-sided, not
LFO wobble. The suite's "width control widens (corr drops)" assertion passes because correlation
does drop — it just drops for the wrong reason.

**Fix:** decorrelate the side term from the mid term (e.g. use `y3 - y6` measured *before* the mid
sums `x`, or high-pass the difference), and add an L/R energy-balance assertion to the suite.

#### H8 · `LiveCore` collapses genuinely wide material
`src/monolock-engine.generated.js:687-693`

The offline engine backs off per band via `autoS = 1 - smoothstep(0.90, 0.98, bandPre)`, which is
what makes the suite's "wide stays transparent" case pass. `LiveCore` has no equivalent — only the
coherence gate `ss(0.25, 0.6, C)`. On the suite's own `makeTest('wide')` material:

```
input correlation                      0.288
OFFLINE processAll,   strength 1.0     0.323   PASSES the <0.5 criterion
LIVE  LiveCore W=512, strength 1.0     0.606   *** FAILS the same criterion ***
LIVE  LiveCore W=1024, strength 1.0    0.538   *** FAILS the same criterion ***
```

The live path narrows material the offline path deliberately leaves alone. There is no LiveCore
counterpart to the offline "wide" test, which is why this is unmeasured.

**Fix:** port the per-band auto-amount into `LiveCore`, or document the live path as a deliberately
more aggressive mode. Either way, add the wide-material test to the live suite.

### MEDIUM

#### M1 · Reverb passes dry SIDE signal at 100 % wet
`src/monofx-reverb.js:70` — the mid path crossfades (`M*(1-mix)`) but the side path uses a
half-strength law (`S*(1-mix*0.5)`). At `mix=1` the dry mid is gone but half the dry side remains.
Pure-side input (`M=0`, so the FDN is never excited), `mix=1, width=0`:
`input RMS 0.35355 -> output RMS 0.17678`, i.e. **-6.02 dB of dry signal out of a 100 %-wet reverb**.
On an aux send this reprints the source. Fix: use `(1-mix)` on both paths.

#### M2 · Delay MIX is a wet send level, not a dry/wet
`src/monofx-delay.js:50` — `mOut = M + mix*mWet` keeps dry at unity, so 100 % wet is unreachable.
The other three cores all crossfade. On a 100 %-wet aux send the dry source is reprinted at unity
(`mix=1`, 1000 ms delay, first 100 ms of output peaks at `1.000000`), summing with the channel's own
dry path. Fix: `M*(1-mix) + mix*mWet`, or rename the control to SEND.

#### M3 · Phaser feedback is in phase at DC: +14.8 dB subsonic boost
`src/monofx-phaser.js:35` — a first-order allpass has `H(1)=+1` for any coefficient, so the six-stage
cascade is unity-gain and zero-phase at DC regardless of the LFO. The one-sample-delayed feedback is
therefore always positive at DC: `x = M/(1-fb) = 10M` at `fb=0.9`.

```
f=0Hz   +14.8 dB      f=20Hz  +11.7 dB      f=55Hz  +5.5 dB
f=5Hz   +14.5 dB      f=30Hz   +9.6 dB      f=120Hz +0.2 dB
```
A DC step of 1.0 settles at 5.4986. Fix: a DC blocker in the feedback path.

#### M4 · `stable at max settings` is false-green — it never inspects the right channel
`tests/monofx-cores.test.js:95` — `const v = s.oL[i]` only. Because of H7 the phaser's peak lives in
`oR`. With every parameter at max and a 10 Hz→20 kHz log sweep: `peakL = 4.73, peakR = 15.37`
(+23.7 dBFS) against a `peak < 12` threshold. The suite prints `peak 1.18` and passes.
Fix: check both channels, and use sustained material as well as transient.

#### M5 · The bass-mono crossover moves with the sample rate
`src/monolock-engine.generated.js:645` — `fHi = 180*(512/W)*(sr/48000)` pins the crossover to a *bin
index*, not a frequency:

```
W=512   44100 -> 165 Hz    48000 -> 180 Hz    96000 -> 360 Hz    192000 -> 720 Hz
W=1024  48000 ->  90 Hz    96000 -> 180 Hz    192000 -> 360 Hz
```

The same session at 96 kHz forces everything below 360 Hz to mono. The UI faithfully displays the
wrong value (`prototypes/monolock-prototype.html:1399`). Fix: pick a fixed frequency and derive the
bin from it.

#### M6 · GCC-PHAT cannot find negative correlation peaks
`src/monolock-engine.generated.js:48-52` — `let best=0; ... if(v>best)`. Polarity-inverted material
that *also* has a time offset scores `conf=0.009`, far under the 0.25/0.3 thresholds, so no
alignment is applied:

```
R = +(L delayed 5 ms):  corr 0.294 -> 1.000   stage-1 lag applied: -240.00 samples
R = -(L delayed 5 ms):  corr -0.294 -> 0.861  stage-1 lag applied:    0.00 samples
```

The spectral stage then has to repair both the flip and the offset by rotation alone, and lands 0.14
short. Failure is graceful (it declines rather than misaligning), and delays beyond the 20 ms
`maxLag` also decline gracefully — but a whole material class is silently unserved. Fix: search
`|v|` and carry the sign as a polarity decision.

#### M7 · `LiveCore` estimators freeze through digital silence
`src/monolock-engine.generated.js:689-693` — the `mag >= 1e-9` gate skips both the update *and* the
decay branch, so exact digital silence freezes the rotation instead of relaxing it:

```
after 1 s of anti-phase audio: max|rotLa| = 1.5708 rad
```

## 2. Verified correct — do not "fix" these

Recording what was checked and cleared matters as much as the defect list, because several of these
look wrong at a glance.

- **Mono-sum width invariance holds.** Full parameter-extreme cross product (81 combinations per
  core) × drums and fully decorrelated pink × six sample rates (22 050 / 44 100 / 48 000 / 88 200 /
  96 000 / 192 000). Worst deviation anywhere `4.4e-16` (phaser), `2.2e-16` (others). No NaN/Inf in
  any combination. The residual is output rounding, not width leakage.
- **The reverb feedback matrix is exactly right.** `h = 0.25*sum` with `N=8` is exactly `2/N`,
  matching `docs/architecture.md:89`. Building the 8×8 matrix of the coded map
  `f_j = l_{(j+3)&7} - 0.25*sum` gives `max|AᵀA - I| = 0` exactly in float64, and random-vector norm
  ratio `1.000000000000000`. (`1/N` would give `0.935` — the code is not making that mistake.)
  End-to-end losslessness confirmed: with damping disabled and `g=1`, total line energy holds at
  `9.800000000e-1` for 27+ seconds.
- **The COLA constants are right**, and verified the way CLAUDE.md §5 demands — by summing the actual
  windows, not from memory: `hop=W/8` sums to `3.999999821..4.000000137` (code divides by 4);
  `hop=W/4` sums to `1.999999875..2.000000118` (code divides by 2).
- **`mix=0` is bit-transparent** on all four cores (`-600.0 dBFS`).
- **The decay law is correct.** `g = 10^(-3*len/(decay*sr))` gives measured T30 of
  0.260 / 0.908 / 1.969 / 5.166 / 10.394 s for decay settings 0.3 / 1 / 2.2 / 6 / 12 s.
- **The LCG is exact.** `(s*1664525 + 1013904223) >>> 0` was suspected of losing bits, but the
  maximum intermediate is `7.1491e15` against a `9.0072e15` mantissa limit — 2 000 000 iterations
  match exact BigInt arithmetic with **0** mismatches. Same for the engine's `pink()`.
- **The "60 assertions" claim was correct** (counted: 60). The suite is now 80.
- **In-place processing is safe** on all four cores (`outL === inL` matches out-of-place exactly).
- **The delay glide cannot produce an unsafe read index** — slamming `time` between 30 and 1500 ms
  every 256 samples for 2 s never brings `dCur` below 16 540 samples, and never produces a
  non-finite sample. Buffer headroom is adequate at every rate from 8 kHz to 384 kHz.
- **`extract-engine.js` fails loudly, not silently.** Multiple `<script>` tags, attributed tags, and
  a literal `</script>` inside a string all produce a FATAL abort or a TypeError rather than a
  quietly truncated engine. The current prototype has exactly one `<script>` tag and no top-level
  declaration the four export regexes miss.
- **The WAV header is correct** (RIFF/fmt/data sizes, PCM tag, channel count, byte rate, block
  align, bit depth) and the int16 conversion **clamps** rather than wrapping.
- **`LiveCore` at `strength = 0` is transparent** (`-122.9 dBFS`).
- **No non-determinism anywhere in the DSP** — no `Math.random`, `Date`, or `performance.now` in any
  core or in the extracted engine region.
- **The mono audition matrix is mathematically correct** (four 0.5 gains into a merger gives
  `0.5L+0.5R` on both outputs).

## 3. What this means for the JUCE port

The build order in `CLAUDE.md` §4 puts `LiveCore` at step 4 and the offline engine at step 5. C1,
C2 and H1 all live in `LiveCore`'s streaming layer — not in its DSP, which is fine. **Fix the FIFO
and the latency contract before porting anything**, because the JS version's buffering model cannot
survive contact with a real host, and porting it line-for-line propagates all three bugs into C++
where they are harder to find.

Two more things worth deciding before the port rather than after:

1. **Parameter validation has no owner.** Every core is configured by `Object.assign(core, msg)`
   with no clamping. The prototype UIs happen to be safe (their knob mapping clamps to
   `[min,max]`), so this is latent rather than live — but L1, L2 and L3 are all instances of the
   same missing contract, and in JUCE the natural place for it is `NormalisableRange` on the APVTS.
   Decide that the core clamps its own inputs, or that the parameter layer does, and write it down.
2. **The suite's assertions need to cover both channels and both edges.** M4 (only `oL` is checked),
   H2 (only the middle of the buffer is checked) and M8 (only one of two enhancement stages is
   asserted) are the same mistake three times: the assertion is narrower than the claim it is
   standing in for. Porting these to Catch2 verbatim ports the blind spots too.

## 4. Method
